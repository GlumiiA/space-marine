# Отчет по внедрению L2 JPA Cache с Ehcache

## Обзор реализации

В проект внедрен **L2 JPA Cache** с использованием **Ehcache** в качестве провайдера кэширования. Реализована возможность включения/отключения логирования статистики (cache hits, cache misses) через **AOP (Aspect-Oriented Programming)**.

## Архитектура решения

### 1. Уровни кэширования

```
┌─────────────────────────────────────┐
│   Controller Layer                  │
│   (REST API для управления кэшем)   │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│   Service Layer                     │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│   Repository Layer                  │  ← AOP Aspect перехватывает вызовы
│   (Логирование cache hits/misses)   │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│   Hibernate L2 Cache (Ehcache)      │  ← Кэширование сущностей
│   @Cache(usage=READ_WRITE)          │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│   Hibernate L1 Cache                │  ← Автоматический (Session)
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│   PostgreSQL Database               │
└─────────────────────────────────────┘
```

### 2. Компоненты системы

#### 2.1. Entity классы с аннотацией @Cache
- `SpaceMarine.java`
- `Chapter.java`
- `Coordinates.java`
- `User.java`

Все entity помечены аннотацией:
```java
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
```

#### 2.2. CacheConfig.java
- Инициализирует Hibernate Statistics
- Периодически логирует общую статистику (каждые 60 секунд)

#### 2.3. CacheStatisticsAspect.java (AOP)
- Перехватывает все вызовы методов репозиториев
- Логирует cache hits/misses для каждой операции
- Управляется через флаг `app.cache.statistics.enabled`

#### 2.4. CacheController.java
- REST API для управления кэшем:
  - `POST /api/cache/statistics/enable` - включить логирование
  - `POST /api/cache/statistics/disable` - отключить логирование
  - `GET /api/cache/statistics` - получить статистику
  - `POST /api/cache/clear` - очистить кэш
  - `GET /api/cache/regions` - детальная статистика по регионам

## Параметры конфигурации Ehcache

### ehcache.xml - основной файл конфигурации

#### 1. Параметр: `heap unit="entries"`
**Значение:** 10000 для default, 5000 для SpaceMarine, 2000 для Chapter

**Описание:** Максимальное количество объектов, хранящихся в heap памяти JVM.

**Влияние на уровень хранения:**
- **HEAP (используется):** Хранение в оперативной памяти JVM
  - ✅ Преимущества: Очень быстрый доступ (наносекунды)
  - ❌ Недостатки: Ограничен размером heap, может вызвать OutOfMemoryError при нехватке памяти
  - 📊 Использование: Для часто используемых "горячих" данных
  
- **OFF_HEAP (не используется):** Хранение вне heap в оперативной памяти
  - ✅ Преимущества: Больше места, не влияет на Garbage Collection
  - ❌ Недостатки: Медленнее чем heap (требуется сериализация/десериализация)
  - 📊 Использование: Для больших объемов данных
  
- **DISK (не используется):** Хранение на жестком диске
  - ✅ Преимущества: Очень большой объем, данные сохраняются при перезапуске
  - ❌ Недостатки: Медленный доступ (миллисекунды)
  - 📊 Использование: Для редко используемых данных или персистентного кэша

**Рекомендации для вашего проекта:**
- SpaceMarine (5000 entries) - основная сущность, средняя нагрузка
- Chapter (2000 entries) - справочник, редко меняется
- Coordinates (3000 entries) - вспомогательная сущность
- User (1000 entries) - небольшое количество пользователей

#### 2. Параметр: `ttl (time-to-live)`
**Значение:** 10-30 минут в зависимости от сущности

**Описание:** Время жизни записи в кэше после создания, независимо от частоты доступа.

**Влияние на уровень хранения:**
- Короткий TTL (5-10 минут): Данные часто обновляются, нужна свежесть
- Средний TTL (15-20 минут): Баланс между производительностью и актуальностью
- Длинный TTL (30+ минут): Статические данные (справочники)

**Конфигурация в проекте:**
```xml
SpaceMarine: ttl=15 минут  (часто меняются, но не критично)
Chapter: ttl=30 минут      (справочник, редко меняется)
Coordinates: ttl=15 минут  (вспомогательные данные)
User: ttl=20 минут         (относительно стабильные данные)
```

#### 3. Параметр: `tti (time-to-idle)`
**Значение:** 5-15 минут

**Описание:** Максимальное время простоя - если к записи не обращались, она удаляется.

**Влияние на уровень хранения:**
- Автоматическое освобождение памяти от неиспользуемых данных
- Предотвращает переполнение кэша "холодными" данными
- Улучшает hit ratio за счет хранения только "горячих" данных

**Конфигурация в проекте:**
```xml
SpaceMarine: tti=10 минут  (умеренная активность)
Chapter: tti=15 минут      (стабильные запросы)
Coordinates: tti=10 минут  (зависит от активности)
User: tti=10 минут         (сессии пользователей)
```

#### 4. Параметр: `jsr107:mbeans enable-statistics="true"`
**Описание:** Включает сбор статистики через JMX MBeans

**Влияние:**
- Позволяет отслеживать cache hits/misses
- Необходимо для работы Hibernate Statistics
- Минимальное влияние на производительность (< 1%)

#### 5. Eviction Policy (неявный)
**Используется:** LRU (Least Recently Used) - по умолчанию в Ehcache

**Описание:** Когда кэш заполнен, удаляются записи, к которым дольше всего не обращались.

**Влияние на уровень хранения:**
- Обеспечивает оптимальное использование памяти
- Сохраняет "горячие" данные, удаляет "холодные"

## Конфигурация Hibernate (application.properties)

```properties
# Включение L2 кэша
spring.jpa.properties.hibernate.cache.use_second_level_cache=true

# Включение query cache (кэширование результатов запросов)
spring.jpa.properties.hibernate.cache.use_query_cache=true

# Использование Ehcache как провайдер L2 кэша
spring.jpa.properties.hibernate.cache.region.factory_class=org.hibernate.cache.jcache.JCacheRegionFactory
spring.jpa.properties.hibernate.javax.cache.provider=org.ehcache.jsr107.EhcacheCachingProvider

# Путь к конфигурации Ehcache
spring.jpa.properties.hibernate.javax.cache.uri=classpath:ehcache.xml

# Статистика Hibernate (управляется динамически)
spring.jpa.properties.hibernate.generate_statistics=false

# Флаг для управления логированием через AOP
app.cache.statistics.enabled=false
```

## Механизм управления логированием через AOP

### Как это работает:

1. **По умолчанию логирование ВЫКЛЮЧЕНО**
   ```properties
   app.cache.statistics.enabled=false
   ```

2. **Включение через REST API:**
   ```bash
   curl -X POST http://localhost:8080/api/cache/statistics/enable
   ```
   - Устанавливает `hibernateStatistics.setStatisticsEnabled(true)`
   - Устанавливает `cacheStatisticsAspect.setCacheStatisticsEnabled(true)`
   - AOP аспект начинает перехватывать вызовы репозиториев

3. **AOP аспект логирует операции:**
   ```java
   @Around("execution(* ru.itmo.is.space_marine_backend.repository..*(..))")
   public Object logCacheStatistics(ProceedingJoinPoint joinPoint) {
       // Замеряет cache hits/misses до и после вызова метода
       // Логирует разницу (операции для данного вызова)
   }
   ```

4. **Пример вывода в логах:**
   ```
   L2 Cache Statistics for method: SpaceMarineRepository.findById
     Cache Hits: 1 | Cache Misses: 0 | Cache Puts: 0
     Hit Ratio for this operation: 100.00%
   ```

5. **Отключение через REST API:**
   ```bash
   curl -X POST http://localhost:8080/api/cache/statistics/disable
   ```

## Преимущества реализованного решения

1. **Производительность:**
   - Сокращение запросов к БД (cache hits)
   - Быстрый доступ к данным из heap памяти

2. **Гибкость:**
   - Динамическое включение/отключение логирования без перезапуска
   - REST API для управления кэшем

3. **Мониторинг:**
   - Детальная статистика по cache hits/misses
   - Периодические отчеты (каждые 60 секунд)
   - Статистика по регионам (для каждой сущности отдельно)

4. **Прозрачность:**
   - AOP не требует изменений бизнес-логики
   - Кэширование работает автоматически для всех операций

5. **Масштабируемость:**
   - Настройка TTL/TTI под каждую сущность
   - Контроль использования памяти через max-count

## Выводы

1. **L2 кэш работает на уровне SessionFactory** - между всеми сессиями приложения, в отличие от L1 кэша (уровень Session).

2. **Ehcache хранит данные в HEAP памяти** - обеспечивает быстрый доступ, но требует контроля размера кэша.

3. **AOP позволяет управлять логированием** без изменения кода репозиториев - separation of concerns.

4. **Параметры TTL и TTI критичны** для баланса между производительностью и актуальностью данных.

5. **Hit ratio > 70% считается хорошим показателем** эффективности кэша.

## Рекомендации для продакшена

1. Настроить мониторинг через JMX или Spring Boot Actuator
2. Добавить алерты при низком hit ratio (< 50%)
3. Рассмотреть OFF_HEAP storage для больших объемов данных
4. Настроить TTL/TTI на основе реальной статистики использования
5. Использовать распределенный кэш (Hazelcast/Infinispan) для кластера
